<Section label="01 · Overview" title="One place for every project">

TM30 PMS is a project management tool built in-house at TM30 Global. It gives the company one place to plan projects, assign work and see where everything stands, replacing scattered spreadsheets and project files.

Leadership was the primary audience, followed by project managers, then the developers and designers doing the work. Every decision in the product comes back to serving those three groups in that order.

<Section label="03 · The problem" title="No one could see the whole picture">

TM30 was running 20+ projects at once, with progress spread across separate spreadsheets and project files. Keeping up with even one project meant bouncing between documents, which was exhausting.

For the CEO and management, it was worse. There was no single place to answer a simple question: how are our projects doing?

<Callout>
  The goal: one tool where leadership sees everything, and teams manage the work.
</Callout>

</Section>

<Section label="04 · Research" title="Designing for three kinds of people">

I started by working out who the tool was really for. The answer was leadership first.

### How I worked

1. Identified the primary user: TM30's executives.
2. Studied existing project management apps to see which patterns work.
3. Sketched early ideas.
4. Talked directly to executives, project managers and developers, and refined the design with their feedback.

### What each group needed

<Columns cols={3}>
  <Card eyebrow="Priority 1" title="Executives">
    An easy way to see every project and its key metrics.
  </Card>
  <Card eyebrow="Priority 2" title="Project managers">
    A clear way to manage tasks and people.
  </Card>
  <Card eyebrow="Priority 3" title="Developers & designers">
    One simple place to tick off tasks. Nothing more.
  </Card>
</Columns>

The challenge was building a tool powerful enough for managers and simple enough for the people doing the work.

</Section>

<Section label="05 · The product" title="Screen by screen">

Each screen below answers one of those three needs.

<Screen
  n={1}
  title="Dashboard"
  src="/project/tm30-pms/dashboard.png"
  alt="TM30 PMS dashboard with status tiles, project cards and alerts panel"
  caption="Status tiles for the big picture, and an Alerts panel for what needs action"
>

The dashboard is built around the CEO's first question: "What's on fire?" Leaders don't have time to scan 20+ projects to find the ones in trouble, so the screen answers that question the moment it loads.

</Screen>

<Notes>
  <Note n={1} title="Status tiles">
    Ongoing, Completed, On Hold, Pending and Overdue show the state of the whole organization in seconds.
  </Note>
  <Note n={2} title="Alerts panel">
    Surfaces overdue tasks and approaching deadlines, grouped by project, with overdue items in red. Each alert is clickable, so an executive can go from noticing a problem to acting on it.
  </Note>
  <Note n={3} title="Cards or table">
    Cards give a quick visual read of each project. A table suits comparing many projects side by side. A toggle lets each person choose.
  </Note>
  <Note n={4} title="Search, filters and Create">
    A search bar covers project name, status and department. Filters and a date selector sit beside the title, and creating a project is one prominent button away.
  </Note>
  <Note n={5} title="Last sync">
    A small indicator shows how fresh the data is, because leaders only rely on a dashboard they trust.
  </Note>
</Notes>

<Screen
  n={2}
  title="Roles & Permissions"
  layout="split"
  src=""
  alt="Roles and Permissions screen"
>

The tool is role-based, so everyone sees what is relevant to them. Executives see the full portfolio. Project managers see their projects and can assign and manage tasks. Developers and designers see their projects and tasks, without management controls they don't need.

Permissions are also fluid. Each role has sensible defaults, but a person can be given extra permissions they wouldn't have by default, without changing their role.

</Screen>

<Callout>
  Roles set the defaults. Permissions handle the exceptions.
</Callout>

<Screen
  n={3}
  title="HR onboarding"
  layout="split"
  src=""
  alt="HR onboarding screen"
>

A tool only works if the right people are in it. HR is its own role in the system, responsible for onboarding staff, so new people are brought in by the team that owns that process rather than by project managers or developers.

</Screen>

<Screen
  n={4}
  title="Spreadsheet import"
  layout="split"
  src=""
  alt="Spreadsheet import screen"
>

TM30's projects already lived in spreadsheets, and asking teams to re-enter everything by hand would have hurt adoption. Import lets a user bring an existing project in from a spreadsheet and see it in the tool straight away, so teams start with their real projects instead of an empty system.

</Screen>

</Section>

<Section label="06 · Principles" title="What shaped the design">

<Columns cols={3}>
  <Card title="Leadership first">
    The dashboard is the default landing view, built around what executives need to see.
  </Card>
  <Card title="Simple by default">
    Developers see only what they need. Extra power appears through roles and permissions.
  </Card>
  <Card title="Meet work where it lives">
    Import brings spreadsheet projects in, so adoption doesn't start from zero.
  </Card>
</Columns>

</Section>

<Section label="07 · Outcome" title="Built, adopted and still growing">

TM30 PMS was built and put into use at TM30, replacing scattered spreadsheets and files as the place to track projects. Management and teams loved it, and it helped them manage projects better.

The product is now being refined, with new screens and features being added.

</Section>

<Section label="08 · Reflection" title="What I learned">

- **Act on feedback fast.** Each user group pulled the design in a different direction, and the faster I iterated, the better it got.
- **Learn directly from users.** Conversations with executives, project managers and developers shaped the design more than any assumption.
- **Research earlier and deeper.** Next time I would invest more in research before and during design, so decisions rest on evidence.

</Section>
